# Architecture

The React client calls the versioned FastAPI API. FastAPI owns scoring, pass/fail decisions, import transactions, answer history, and OpenAI access. Services coordinate domain rules; repositories isolate SQLAlchemy persistence. MySQL 8 stores UTC timestamps and application settings. The importer streams JSONL, validates before persistence, records job-level and row-level errors, and never mutates source files.

OpenAI is optional: study, scoring, mock exams and stored explanations continue without it. AI output is schema-validated, cached, logged without prompts or secrets, and never silently replaces a provided or administrator-final answer.

Authentication uses an HttpOnly session cookie and resident Passkeys. Managed users use their issued password only to open the first-device registration ceremony; subsequent login starts with an anonymous, short-lived, single-use challenge stored as a hash-backed `exam_passkey_challenges` record, and the discoverable credential identifies the user. The environment-owned administrator instead verifies `INITIAL_ADMIN_USERNAME`/`INITIAL_ADMIN_PASSWORD` on each web login and immediately receives a full session. Both paths keep one active session per account and use the same inactivity/startup revocation rules. Device reset removes Passkey credentials and sessions but keeps the account and learning data. The administrator's offline recovery secret is stored only as a PBKDF2 hash in the environment and can reset administrator device credentials and sessions without creating a login session. Account deletion removes user-owned study attempts, study sessions, mock exams, wrong notes, sessions, and credentials while retaining shared certifications, questions, and AI explanations.

Temporary API or database failures are not treated as authentication failures: only an HTTP 401 response enters the login flow. While a study or mock exam is active, the client stores only user/session/question identifiers, selected choice identifiers, position, and synchronization state in IndexedDB. It never stores question bodies, explanations, or correct answers. Failed study-draft writes remain pending and are replayed idempotently when connectivity returns; mock-exam selections follow the same synchronization rule. Server-saved selections and the UTC exam deadline are restored by the navigation metadata endpoint, and device drafts are removed on normal completion or abandonment and expire after 24 hours.

Study-session creation partitions the eligible question pool using the authenticated user's submitted `exam_study_attempts`: unseen questions are shuffled and placed first, followed by independently shuffled seen questions only when needed. Mock-exam selection remains governed by the certification blueprint rather than study history.

Scheduled notices are stored in `exam_notices`. General and maintenance popups use server-defined display intervals, plain text content, and allow-listed color/weight values. A maintenance popup blocks access only when its separate maintenance-screen option and interval are configured. Those intervals are non-overlapping half-open ranges, and a locked application-setting sentinel serializes competing schedule writes. An application-lifespan scheduler polls the database every `MAINTENANCE_POLL_SECONDS` (default 5), so enforcement does not depend on browser traffic. Five minutes before maintenance, active clients warn learners using server time. At maintenance start, a notice row lock makes finalization idempotent: the last server-synchronized study draft is scored and partially saved (including wrong-note retry semantics), in-progress mock exams are marked `maintenance_cancelled`, general-user sessions are revoked, and administrator sessions remain active. Normal-user protected API calls are denied throughout the maintenance interval. Executed schedules are immutable and cannot be reused. After the interval, clients return to the login screen.
